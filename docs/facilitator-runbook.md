# Operation Lighthouse facilitator runbook

**Private operating reference. Do not project or distribute with the participant
kit.** This is the runtime companion to the approved 18-slide facilitator guide,
not a replacement presentation. Its procedures are prepared; human execution,
live-service verification and pilot approval are still pending.

## Choose the rehearsal boundary

| Mode | Permitted use | Start here |
| --- | --- | --- |
| Local | Synthetic instructor, participant CLI and browser on the same machine; memory is lost on API restart. Never expose the loopback server through a tunnel or shared proxy. | [Local operating guide](local-workshop.md) |
| Hosted | Separately authorized environment with real Entra, managed identity, Cosmos, pinned Key Vault/Blob references and SignalR. One configured API replica; no high-availability claim. | [Hosted preparation and deployment stages](hosted-workshop.md) |

No Azure provisioning, deployment, role changes or outage injection is authorized
by this document. Obtain separate approval for the exact environment and any
disruptive drill. Do not reuse a real event for a synthetic rehearsal.

Assign a lead facilitator, a support/operator role and an observer/timekeeper.
Record actual assignments privately before starting; these are responsibilities,
not prefilled people or evidence of availability. The event creator needs
`event-admin` in hosted mode. Another instructor does not automatically share
ownership; do not grant `platform-admin` merely to work around that boundary.

## Before the clean authoring rehearsal

1. Choose a source revision and starter set. Record the actual Git commit,
   runtime mode, application versions and recovery/validator versions. For
   hosted work, also record the approved release manifest's image digests,
   campaign digest and signing **version reference**, never its value.
2. Follow the mode-specific startup guide. In hosted mode, complete the real
   tenant, resource permissions, exact origin, token renewal and immutable
   artifact checks first. A bootstrap placeholder or green static dashboard
   health endpoint is not evidence of a usable workshop API.
3. Build the source-backed CLI using the participant guide. Verify the actual
   delivery on a clean participant machine; there is no published public npm
   participant package. Do not distribute only `dist\cli.js` without its runtime
   dependencies, or put the full repository/answer fixtures in the agent workspace.
4. Create a fresh synthetic event and keep its ID/code in the approved private
   operator store outside source control. Open the lobby and event, then Mission 1.
   Open its public-only link in a separate projector window.
5. Prepare a fresh participant home and starter workspace. Do not reuse an
   existing person's credentials or exercise files. Verify configuration in the
   actual VS Code terminal; another terminal's variables are not inherited
   reliably by an already-running editor.
6. Verify the real account's Copilot entitlement, permitted session target,
   available model and approved tools. A detected extension is insufficient.
   Confirm popup sign-in is acceptable for the actual instructor/tenant/browser;
   it remains an implementation assumption requiring review.
7. Agree on a diagnosis time limit and a labeled still-based fallback for each
   demonstration. Keep private solutions, tokens and raw network recordings off
   shared screens and out of the participant workspace.

### Observe the authoring, not just the result

Have the participant follow [the participant guide](participant-guide.md)
without copying completed regression fixtures. The observer records the actual
VS Code version, selected harness/model, approved tool names and any assistance.
Do not record account identifiers, credentials or raw chat histories.

Run `config show`, `auth`, `connectivity` and `preflight` in the terminal the
participant will actually use. All required checks must pass after registration.
A pre-registration authentication warning is expected; it is not a passed join.
Have the participant create/select a workspace `.agent.md` file and produce a
synthetic artifact through a real chat session.

| Mission | Human observation and server check |
| --- | --- |
| 1 - Signal in the Storm | Reference the report and `contracts\output.schema.json`; author an assessment, inspect unsupported claims, and distinguish an envelope-valid missing-field example from evaluated server failure. Repair it and inspect authoritative feedback. |
| 2 - Ground Truth | Follow one claim to its report/bulletin citation. Explain a contradiction, an unknown and the boundary around untrusted instructions. Submit the participant's own evidence package. |
| 3 - Connected City | Use the approved terminal tool to discover and call the real CLI operations. Observe the intentional forecast failure, bounded actual retry, successful route/shelter evidence and supported recommendation. Receipt replay and a new invocation must be distinguishable. |
| 4 - Specialist Network | Demonstrate the chosen harness invoking the intended bounded specialists, carrying evidence through their handoffs and using a separate reviewer. If only a JSON plan was authored, record contract-only evidence and leave actual specialist execution pending. |
| 5 - Restore the Lighthouse | Gather fresh mission-scoped receipts from four successful tool sources, inspect the combined allocation against observed inventory, follow two handoffs and independently review the final package. Observe server acceptance separately from any claimed human approval. |

For every mission, record the artifact's digest, safe submission reference,
required-rule outcome, observed difficulty and elapsed time. Validate the
envelope, submit with a saved key, then read status; never treat a screenshot
or generated JSON as an accepted mission. Open the next mission only after
checking progression. The facilitator may coach without silently supplying a
completed solution or redefining advanced objectives as core requirements.

Receipts cannot move between units or missions. Proposed allocations do not
change inventory, routes, shelters or the electrical grid. Do not teach the
synthetic regression's 84% result as the only valid participant plan.

### Failure and recovery drills

Use only approved synthetic sessions. Browser-side network blocking can exercise
client failure without changing Azure resources. Infrastructure restarts, role
changes and dependency failures require separate operator authorization.

| Drill | Action and required observation |
| --- | --- |
| Participant reconnect | Reconnect with the same API URL and participant home. Unit identity and prior evaluated work remain the same; do not register another unit to repair a token. |
| Instructor renewal and denial | Exercise normal token renewal, an account without the required role, another owner's event and logout in the real tenant. Unauthorized access must fail; private state clears on logout. Do not capture tokens or assume a cached sign-in proves authorization. |
| Lost mutation response | With a synthetic event, interrupt the reply to a creation/command or CLI submission. In the same instructor tab use **Retry the same action**; for CLI reuse the exact key/body. Verify one effect, unchanged command identity and no duplicate contribution. Never issue a replacement merely because a reply was lost. |
| Instructor tab/account loss | First resolve pending actions. Reopen, sign in, enter the saved event ID and select refresh to recover known event state. An unknown creation outcome or lost code requires authorized reconciliation against durable creation/event records; no self-service event listing or automatic browser journal exists. If the outcome cannot be established, stop rather than create a duplicate. |
| Paused mission/version conflict | Pause through the real UI, verify explicit participant rejection, then resume. After a definitive version conflict, refresh and issue the intended action with a new command/key using the current version. This differs from retrying an uncertain result. |
| 429, bounded queue or temporary 503 | Respect `Retry-After`; no tight retry loop, new identity or key change to evade budgets. Preserve the original body/key for uncertain writes. Check classroom shared-IP behavior rather than assuming per-person ingress addresses. |
| API or HTTP snapshot outage | The public page must hide stale results and identify unavailability. Restore access and wait for a fresh snapshot. Late SignalR frames must not revive results while HTTP is unhealthy. Do not substitute sample scores. |
| SignalR-only outage | In hosted mode, block only the SignalR service in the rehearsal browser. Fresh HTTP snapshots remain usable. Restore it and verify scoped delivery/reconciliation without duplicate credit. Service publication acceptance alone is not proof the projector rendered an update. |
| API restart | Local mode loses the event: create a new synthetic event/home and rejoin. Hosted mode must preserve units, feedback, receipts, replay and recovery with the same keys/catalog; refresh/reconnect the existing identity. A changed signing key or incompatible catalog is not a recovery strategy. |
| Startup dependency failure | In a separately approved hosted test, unavailable/malformed signing material or campaign configuration must prevent readiness, never select memory state. After correction, verify the original event's integrity. Do not rotate a live event's key or use a mutable campaign artifact as a shortcut. |

Capture only safe error codes, HTTP status, correlation references and observed
state transitions. Do not save HAR files, raw browser consoles or WebSocket
URLs: they can contain bearer or short-lived public connection tokens.
The automated transport doubles are useful baselines, not a replacement for
the authorized hosted restart and failure exercises.

### Close, restore and roll back deliberately

Close the event in the operational UI with a reason and `CLOSE LOCAL EVENT`
locally or `CLOSE EVENT` when hosted. Confirm submissions are closed before
switching to the final public slide. Keep attendance and hands-on participation
separate from scores and recognition examples.

Before hosted delivery, the operator must document and rehearse a compatible
rollback using reviewed immutable release references, as well as backup/restore
and retention. A consistent restore must preserve routing, event, replay,
receipt and scoring state together. No automated cross-version migration,
signing-key rotation, result-export UI or retention cleanup is supplied here.
If compatibility or uncertain-write reconciliation is unknown, stop admission
and escalate; do not switch releases or delete documents to make health green.

Remove only specifically identified rehearsal artifacts under the agreed
retention policy. Preserve needed incident evidence privately, revoke access
through approved processes and never delete a repository, user home or shared
credential directory as an event reset.

## Controlled pilot and go/no-go

After resolving internal-rehearsal blockers, run a pilot with **up to 20 actual
participants** in the intended environment. Record people and units separately;
50 synthetic HTTP clients are not pilot attendance. Confirm facilitator/support
availability, accessible materials, the actual participant delivery path and
the approved privacy/retention process before inviting participants.

Use the same agenda and failure/fallback boundaries. Record time to join,
authoring/tool problems, interventions, mission outcomes and qualitative learning
feedback. The 85% Missions 1-3, 60% Mission 4 and 40% Mission 5 targets in I16 are
planning goals for active units, not measured results or certificate thresholds.
Recovery's eligible-unit denominator is different from these learning metrics.

For each run keep a restricted record outside source control with these fields:

| Record | Required contents |
| --- | --- |
| Context | Actual UTC date, source/release references, mode, versions, locale, harness/tools, observed participant/unit counts and assigned operating roles |
| Gate evidence | Gate/drill ID, expected and observed behavior, pass/fail/not-run, sanitized artifact references/digests and observer confirmation |
| Findings | Reproduction steps, affected scope, impact, release-blocking decision, responsible role and actual agreed resolution date |
| Resolution | Corrective commit/release, repeated check and actual outcome; an intended fix is not a verified resolution |
| Decision | Explicit go/no-go by the accountable operator/facilitator, remaining limitations and the environment/release to which approval applies |

Keep personal attendance and certificate records in their approved private
system. Never commit identities, conversations, codes, tokens or personalized
certificates. Do not copy this blank record specification into a report and
mark observations as completed.

Cross-event access, leaked credentials/private projection, lost or duplicate
accepted work, forged-receipt acceptance, inaccessible core operations, missing
authoring/tool access, or an unverified recovery path block release. Unresolved
hosted permissions, rollback/restore, retention and classroom capacity also block
public-event approval. Log usability/timing findings and agree their disposition;
do not hide them with a static success display.

Update R08/L08 and TASK-800 through TASK-810 only when their actual acceptance
criteria have evidence. The facilitator supplement and offline automation can
be complete while the human rehearsal, pilot and final go/no-go remain pending.
